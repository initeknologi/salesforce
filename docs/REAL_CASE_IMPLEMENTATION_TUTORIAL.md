# Real-World Salesforce Case — Implementation Tutorial

## Goal

Build an MVP for a global energy-storage company:

> A salesperson closes an Opportunity for battery products. Salesforce creates a draft sales order. After review and submission, the order is synchronized asynchronously to Microsoft Dynamics 365 Business Central. A service agent can then view the customer’s installed battery Asset and process a warranty Case. Integration failures are logged, assigned, and visible on an operational dashboard.

This is a simulated enterprise case study. Treat it as a reference implementation, not a copy of any one customer org.

## What Already Exists

The repository already provides:

- `Sales_Order__c`
- `Integration_Log__c`
- `Order_Sync_Event__e`
- Apex service and trigger-handler layers
- Platform Event → Queueable integration
- Batch Apex and retry support
- Inbound and outbound REST endpoints
- Business Central-style Node.js mock server
- LWC order synchronization panel
- Order dashboard
- Data migration LWC
- Permission Set and Custom Metadata
- Flow for failed-sync follow-up
- Apex tests and GitHub Actions

The repo already includes these pieces — extend them rather than duplicating.

```text
force-app/main/default/objects/Opportunity/fields/
```

### `ERP_Sync_Status__c`

- Type: Picklist

- Default: Not Ready

- Type: Lookup to `Sales_Order__c`
- Purpose: traceability from Opportunity to integration order

## 1.3 Extend `Sales_Order__c`

Add:

- Type: Lookup to Opportunity
- Delete constraint: SetNull

### `Currency_Code__c`

- Type: Text, length 3
- Example: SEK

### `Correlation_Id__c`

- Type: Text, length 80
- External ID: true

# Phase 2 — Build the Sales Cloud Process

## 2.1 Configure products and price book

Create sample products in Salesforce:

- Battery Cabinet 48V
- Modular Battery Cabinet
- Installation Service
- Monitoring Subscription

Use the Standard Price Book and SEK prices.

For the demo, one Opportunity Product is enough. Two or three products make the process more realistic.

## 2.2 Create a Record-Triggered Flow

Flow API name:

```text
Opportunity_Closed_Won_Create_Sales_Order
```

Configuration:

- Object: Opportunity
- Trigger: record updated
- Run: after save
- Entry conditions:
  - `StageName Equals Closed Won`
  - `IsWon Equals True`
  - `Generated_Sales_Order__c Is Null`
- Optimize for: Actions and Related Records

Flow elements:

### Element 1 — Get existing sales order

Query `Sales_Order__c` where:

```text
Opportunity__c = $Record.Id
```

This is a second idempotency guard.

### Element 2 — Decision

Outcomes:

- `Order Does Not Exist`
- `Order Already Exists`

### Element 3 — Create Sales Order

Map:

```text
Account__c       = $Record.AccountId
Opportunity__c   = $Record.Id
Order_Date__c    = $Flow.CurrentDate
Total_Amount__c  = $Record.Amount
Currency_Code__c = $Record.CurrencyIsoCode (if multi-currency is enabled)
Status__c        = Draft
Correlation_Id__c = "OPP-" & $Record.Id
Description__c   = "Generated from Opportunity " & $Record.Name
```

Create as Draft. Do not synchronize immediately. A salesperson or sales operations user should review the order first.

### Element 4 — Update Opportunity

Set:

```text
Generated_Sales_Order__c = Created Sales Order Id
ERP_Sync_Status__c       = Not Ready
```

### Element 5 — Fault path

Create an error Task assigned to the Opportunity owner, or publish an error event. Do not leave fault connectors unused.

## 2.3 Add a validation rule

Rule on `Sales_Order__c`:

```text
AND(
  ISPICKVAL(Status__c, "Submitted"),
  OR(
    ISBLANK(Account__c),
    ISBLANK(Order_Date__c),
    Total_Amount__c <= 0
  )
)
```

Error:

```text
Account, Order Date, and a positive Total Amount are required before submission.
```

## 2.4 Link order status back to Opportunity

Extend `SalesOrderService.updateOrderAfterSync()`:

- After successful synchronization, update related Opportunity `ERP_Sync_Status__c = Synced`.
- On failure, set it to Failed.

Perform updates in collections where possible. Do not add SOQL or DML inside loops.

For a quick MVP, a small after-save Flow on `Sales_Order__c` can update the Opportunity. For production, prefer a clear single owner for this automation to prevent Apex/Flow overlap.

## 2.5 Add Opportunity page components


```text

```

- Object: Case
- Trigger: created or updated

# Phase 5 — Integration Reliability

## 5.1 Keep callout before DML

Inside Queueable:

1. Query required data.
2. Perform the callout.
3. Update Salesforce records.
4. Write operational logs.

Do not perform DML before the callout in the same transaction.

## 5.2 Implement idempotency

Use:

```text
Sales_Order__c.Correlation_Id__c
```

Send it as:

- `externalId` in the JSON payload
- `Idempotency-Key` HTTP header if supported

The mock ERP must return the original order when the same key is submitted again.

## 5.3 Classify failures

Retry:

- Network timeout
- HTTP 429
- HTTP 500, 502, 503, 504

Do not automatically retry:

- HTTP 400 validation failure
- HTTP 401/403 authentication or authorization
- HTTP 404 configuration/mapping error

Store:

- Error category
- Retry count
- Correlation ID
- First and last attempt time
- Support owner

Adding all these fields is optional for MVP; explain them as production hardening.

## 5.4 Reconciliation

Add a scheduled or Batch Apex design:

```text
ERPOrderReconciliationBatch
```

It selects:

- Submitted orders older than 15 minutes
- Sync Failed orders still eligible for retry
- Synced orders missing an ERP Order ID

For the demo, show the existing `OrderSyncBatch` and explain how it can evolve into reconciliation.

# Phase 8 — Testing

## 8.1 Apex tests

Add tests for:

- Closed Won creates only one Sales Order.
- Duplicate Flow execution does not create a second order.
- Submitted order publishes an integration event.
- Successful callout stores ERP Order ID.
- Timeout and 5xx produce Sync Failed.
- 400 and 401 are not blindly retried.
- Duplicate external ID returns existing ERP order.
- 200-order trigger/bulk scenario.
- Unauthorized inbound callback returns 401.

## 8.2 Flow tests

Use Flow Tests where supported:

- Opportunity not Closed Won: no order.
- Closed Won without Account: expected validation/fault behavior.
- Closed Won with required data: one Draft order.
- Warranty Case: priority, RMA status, and Task created.
- Non-warranty Case: no warranty Task.

## 8.3 Manual end-to-end test

Happy path:

```text
Opportunity Closed Won
→ Draft Sales Order
→ Submit
→ Platform Event
→ Queueable
→ Mock Business Central
→ Synced + ERP ID
→ Integration Log
```

Failure path:

```text
Stop mock ERP
→ Submit/sync order
→ Sync Failed
→ Integration Log
→ Follow-up Task
→ Restart ERP
→ Controlled retry
→ Synced
```

Service path:

```text
Account
→ Asset
→ Warranty Case
→ Triage Flow
→ High priority + Task
→ RMA approved
```
